# 수학 릴스(숏폼) 자동화 파이프라인

학년 블로그 자동화(`.claude/skills/blog-auto/`)와 별개로, **틱톡/릴스용 20~25초 수학 숏폼
영상**을 만드는 파이프라인입니다. 실제 77math 채널(유튜브 쇼츠 `@77math81`)의 레퍼런스
영상들을 기준으로 브랜드 스타일을 맞췄습니다: "호기심 유발 → 접근 → 문제 해결 → 다음 편
궁금증(클리프행어)" 구조를 따르고, 마지막에 `77math` 큐시브 네온 로고(시안 `77` + 마젠타
`math` + 스우시 밑줄)가 네온사인처럼 켜지는 아웃트로로 끝납니다.

## 브랜드 스타일 (레퍼런스 영상에서 추출)

실제 채널 레퍼런스(외심/단위원 시리즈)를 보면 다음 구조가 항상 반복됩니다. 새 주제를
만들 때도 이 구조를 그대로 따라야 "일관성"이 유지됩니다:

- **헤더** (`engine.js`의 `drawHeader`): 좌상단 `학년 · 단원` 브레드크럼, 중앙 큰 흰색
  굵은 제목, 그 아래 시안색 한 줄 부제("이 영상의 핵심 아이디어"). 회차 번호는 넣지
  않습니다(실제 시리즈 번호와 안 맞는 임의 숫자를 넣으면 안 되기 때문).
- **본문 다이어그램**: 차분한 고정 시점의 네온 선 구성 도형(원, 삼각형, 각도 표시 등).
  레퍼런스 영상은 카메라가 계속 회전하거나 화면 가득 색색의 파티클이 날리는 식의 "TikTok
  글리치" 연출을 쓰지 않습니다 — 선이 차분하게 그려지고, 색은 개념별로 고정 배정됩니다.
- **하단 스텝 카드** (`drawStepCard`): 반투명 다크 카드에 단계 라벨(시안, 작게) + 헤드라인
  (흰색, 굵게) + 보조설명(회색, 작게). 카드 바로 아래 얇은 진행률 바(`drawProgressBar`).
- **장식은 절제**: 화면 구석에 고정된 작은 반짝임 아이콘(`drawSparkle`) 1~2개 정도만.
  화면을 가로지르는 색종이 폭죽 같은 연출은 브랜드에 없습니다.
- **아웃트로**: `drawBrandLogo` — 검정 배경에 `77`(시안)+`math`(마젠타, 이탤릭)+마젠타
  스우시 밑줄이 좌→우 와이프로 네온사인처럼 켜지고 끝. 타이핑 효과나 산산조각 효과는
  실제 브랜드에 없으므로 쓰지 않습니다.
- **색상은 개념별로 구분**: 케이스별 곡선 색이 서로 겹치지 않도록 주의합니다(예: 자르는
  평면 표시선이 노란색이면, 노란색은 곡선 색으로 재사용하지 않기).

## 플랫폼 안전 영역 (업로드하면 잘려 보이는 문제)

만들어둔 영상을 실제로 틱톡/릴스/쇼츠에 올리면, 앱 자체 UI가 영상 위에 고정으로 덮입니다:
- **우측**: 좋아요·댓글·공유·북마크 아이콘 열
- **하단**: 계정명 + 캡션 + 음원 정보 + 앱 자체 진행바

이 영역에 스텝카드나 로고 같은 핵심 콘텐츠가 들어가면 업로드 후 가려집니다. 그래서:
- `engine.js`의 `SAFE`/`SAFE_X0`/`SAFE_X1`/`SAFE_Y0`/`SAFE_Y1`/`SAFE_CX`가 실제로
  안전한 영역을 정의합니다. **다이어그램의 중심 x좌표는 `WIDTH/2`가 아니라 `SAFE_CX`를
  쓰세요** — 그래야 우측 아이콘 열 밑으로 도형이 들어가지 않습니다.
- `drawStepCard`/`drawProgressBar`는 이미 이 안전 영역 기준으로 기본 위치가 맞춰져
  있습니다(진행률 바는 일부러 하단이 아니라 헤더 바로 아래·상단에 둡니다 — 하단은
  항상 캡션에 가려지기 때문). 기본값을 그대로 쓰면 자동으로 안전합니다.
- 도형이 커지거나(예: 궤도가 이심률에 따라 늘어나는 경우) 화면을 넓게 쓰는 주제라면,
  `player.html?story=<topic>&safe=1`로 열어서 빨간 점선 가이드 안에 다 들어오는지
  눈으로 확인하세요. `render.mjs --safe` 플래그를 쓰면 확인용 mp4에도 가이드가
  찍혀 나옵니다(**`--safe` 없이 렌더링해야 최종 결과물에 가이드가 안 나옵니다**).

## 왜 이런 구조인가

- **완전 코드 기반**: PNG 프레임을 일일이 타임라인 편집기로 만드는 대신, 캔버스를
  `render(ctx, t)` 함수 하나로 정의합니다. `t`(초)를 넣으면 항상 같은 프레임이 나오는
  **결정론적** 렌더링이라, 서버 성능과 무관하게 매번 똑같은 결과가 나옵니다.
- **주제 = 데이터가 아니라 코드**: 원뿔곡선처럼 "도형이 실시간으로 계산되는" 주제가
  많아서, 스토리보드를 JSON이 아니라 JS 모듈로 둡니다(원뿔 단면 곡선 수식 등 로직이 필요).
- **인터넷 접속 불필요**: 웹폰트/CDN 라이브러리 없이 시스템 폰트 + Canvas API만 사용해서
  오프라인 렌더 서버에서도 그대로 동작합니다.

## 폴더 구조

- `engine.js` — 주제에 종속되지 않는 범용 헬퍼. 브랜드 레이아웃(`drawHeader`,
  `drawStepCard`, `drawProgressBar`, `drawBrandLogo`, `drawSparkle`)과 저수준 드로잉
  프리미티브(네온 글로우 선, 진행률 기반 선 그리기, 3D 프로젝션, 배경)가 함께 있습니다.
  `glitchText`/`drawShatter`/`drawSparks`도 남아있지만 현재 브랜드 스타일에는 맞지 않아
  `conic_sections.js`에서는 쓰지 않습니다 — 굳이 다른 톤이 필요할 때만 참고하세요.
- `storyboards/<topic>.js` — 주제별 장면 연출. `T`(타임라인), `render(ctx, t)`,
  `DURATION`, `meta`(제목/해시태그 후보)를 export 해야 합니다.
- `player.html` — 브라우저에서 스토리보드를 재생하는 뷰어.
  - 미리보기(라이브 재생): `player.html?story=conic_sections`
  - 캡처 모드(Playwright 전용, 자동재생 안 함): `?story=conic_sections&capture=1`
- `render.mjs` — Playwright로 프레임을 한 장씩 정확히 캡처한 뒤 시스템 ffmpeg으로
  mp4(H.264)로 인코딩하는 CLI.

## 사용법

### 0) 최초 1회 환경 준비
```
ln -sfn /opt/node22/lib/node_modules/playwright node_modules/playwright
```
(전역 설치된 Playwright를 로컬에서 `import`할 수 있게 심볼릭 링크만 겁니다. `node_modules/`는
git에 커밋하지 않습니다 — `.gitignore` 참고.)

시스템에 `ffmpeg`(libx264 포함)가 없다면 설치합니다:
```
sudo apt-get update && sudo apt-get install -y --no-install-recommends ffmpeg
```
(Playwright에 내장된 ffmpeg은 webm/vp8 스크린캐스트 전용 경량 빌드라 mp4 인코딩이 안 됩니다.)

### 1) 브라우저에서 미리보기
```
npx http-server reels -p 8787
# 브라우저에서 http://localhost:8787/player.html?story=conic_sections
```

### 2) mp4로 렌더링
```
node reels/render.mjs --story conic_sections --out output/reels/conic_sections.mp4 --fps 30
```
결과: 1080x1920 세로 mp4. `output/`는 `.gitignore`에 포함되어 있어 렌더 결과물은
커밋되지 않습니다(용량 문제 + 회차별 산출물이라 블로그 파이프라인과 동일한 정책).

## 새 주제 추가하기

1. `reels/storyboards/<topic>.js`를 만듭니다. `conic_sections.js`를 템플릿으로 복사하세요.
2. 타임라인은 20~25초 안에서 `HOOK → APPROACH → (문제 해결 비트들) → CLIFF → OUTRO` 순서를
   지킵니다. 매 세그먼트에서 `drawHeader`(제목/부제 고정) + `drawStepCard`(그 순간의
   헤드라인) + `drawProgressBar`를 호출하고, `OUTRO`는 `drawBrandLogo`를 그대로
   재사용하면 됩니다 — "브랜드 스타일" 절을 참고해서 새 도형/색을 추가하세요.
3. `render(ctx, t)` 하나만 export하면 나머지 파이프라인(뷰어, 렌더러)은 그대로 재사용됩니다.
4. `meta.title`/`meta.hashtags`에 후보 제목·해시태그를 적어두면 업로드 시 바로 씁니다.

다음 후보 주제 예시(참고 기획서에서): 무한등비급수 등.

## 시리즈 진행 상황

1. `conic_sections` — 원뿔곡선 (원/타원/포물선/쌍곡선의 정체) → 클리프행어: "우주선의 궤도는?"
2. `eccentricity` — 이심률 e (초점 기준 극좌표 r=ℓ/(1+e·cosθ) 하나로 4가지 곡선을 스윕) → 클리프행어: "e는 어떻게 계산할까?"
3. `eccentricity_formula` — 이심률 계산법 (e=c/a, b로 구하는 대안 공식, 지구/핼리혜성/보이저1호
   실제 사례) → 클리프행어: "진짜 우주선(보이저 1호 등)의 궤도를 계산해보면?"

1~3편은 "원뿔곡선" 시리즈로 서로 이어집니다. 각 편은 직전 편의 클리프행어에 답하고 새
클리프행어로 마무리합니다 — 새 편을 기획할 때는 직전 편의 `T.CLIFF` 카드 문구를 확인하고
거기서 시작하세요.

별도 주제(다른 시리즈):
- `geometric_series` — 무한등비급수 (정사각형 나선 분할로 1/2+1/4+1/8+...=1을 보여주고,
  공식 S=a/(1-r), 0.999...=1·제논의 역설·튕기는 공 실제 사례) → 클리프행어: "모든 무한합이
  항상 답을 가질까?" (발산하는 조화급수로 이어질 수 있는 훅)
- `fibonacci` — 피보나치 수열 (정사각형 나선 1,1,2,3,5,8 + 황금나선 호, 점화식
  F(n)=F(n-1)+F(n-2), 비율의 황금비 수렴, 해바라기씨/솔방울/앵무조개 실제 사례) →
  클리프행어: "정말 모든 자연이 피보나치를 따를까?"
  (AI가 생성한 레퍼런스 영상은 사각형이 서로 안 맞게 겹치고 라벨 숫자도 피보나치가 아니었다
  — `buildFibUnitSquares`/`ARC_RULES`가 왜 정확한 좌표인지는 파일 상단 주석과 소스의
  유도 과정 설명 참고)
- `fibonacci_factcheck` — `fibonacci` 편의 클리프행어에 답하는 후속편. 4가지 유명한 주장을
  "사실/과장" 도장(`drawStamp`)으로 판정한다: 해바라기 씨앗(사실)·앵무조개 황금나선(과장,
  실측 성장비 ≈1.3)·파르테논 신전 황금비 설계(과장, 근거 없음)·식물 잎차례 137.5° 황금각
  (사실, 옥신 확산 메커니즘). 결론에서 "신비가 아니라 최적의 공간 배치"라는 진짜 이유를
  설명 → 클리프행어: "그럼 '황금비 얼굴'은 진짜 있을까?"
- `golden_ratio_face` — `fibonacci_factcheck` 편의 클리프행어에 답하는 후속편. 같은
  "주장→도장→설명" 형식. 아름다운 얼굴=황금비 1.618(과장, 실측 안 맞음)·마르퀴트
  미의 마스크(과장, 실제 얼굴과 안 맞는다는 비판)·동공 확대가 매력도를 높인다(사실,
  심리학 연구로 반복 확인)·얼굴 대칭성(사실, 여러 문화권에서 일관됨). 결론: 매력은
  숫자 하나가 아니라 대칭·평균·건강 신호가 겹쳐서 작동 → 클리프행어: "평균 얼굴이
  가장 매력적일까?" (합성사진 실험)

별도 주제(피보나치/황금비 계열과 무관한 새 방향):
- `prime_spiral` — 울람의 나선(Ulam Spiral). 1~225를 나선으로 배열하고 소수만 표시하면
  대각선을 따라 뭉치는, 지금도 완전히 설명 안 된 패턴이 드러난다. 요청("움직임이 더
  화려하게, 프레임마다 쪼개서")을 반영해 225개 칸을 근-프레임 단위로 빠르게 채우고
  (`renderFill`), 소수가 나올 때마다 짧은 스케일 펄스+미니 버스트를 준다. 대각선은
  연출용으로 그은 게 아니라 실제 소수가 가장 많이 몰린 대각선을 `topDiagonals()`로
  데이터에서 직접 계산해서 그린다. 격자 전체에 은은한 줌/회전(`withGridCamera`)도
  건다 → 클리프행어: "소수는 정말 무한할까?" (유클리드의 증명)

## "화려하게" 만들 때 (더 많은 장면 / 더 강한 포인트가 필요할 때)

브랜드 골격(헤더/스텝카드/진행바/77math 로고)은 유지하면서 에너지를 올리고 싶다면:
- **장면 수를 늘린다**: 한 개념을 한 화면에서 계속 우려먹지 말고, 기하 장면(도형+라벨) ↔
  타이포 장면(큰 숫자/공식만) ↔ 속사포 사례 장면(여러 항목을 빠르게 전환)을 섞는다.
  `eccentricity_formula.js`가 이 패턴의 예시다(설정→공식→대입→대안→실제사례 3연타).
- **"프레임마다 쪼개서" 채우는 연출**: 항목이 많은(수십~수백 개) 데이터를 보여줄 땐
  개별 트윈 없이 `revealCount = floor(progress * N)`처럼 누적 개수만 계산해서 한 프레임에
  하나씩(또는 여러 개씩) 나타나게 한다 — 진짜 데이터가 실시간으로 채워지는 느낌이 난다.
  방금 나타난 항목만 `since = progress - i/N` 같은 값으로 아주 짧게(0.05~0.15) 반짝이게
  하면 트윈 계산 없이도 자연스러운 반짝임이 생긴다. `prime_spiral.js`의 `renderFill` 참고.
- **`withGridCamera` 패턴으로 화면 전체에 카메라 움직임을 건다**: 도형 하나가 아니라
  격자/장면 전체를 `ctx.translate`+`ctx.rotate`(아주 작게, ±0.01~0.02rad)+`ctx.scale`로
  감싸면 은은한 줌/흔들림이 생겨서 화면이 훨씬 덜 정적으로 느껴진다.
- **`drawDust`로 은은한 분위기를 깐다**: `drawSparks`보다 훨씬 조용하고 촘촘한(60~80개)
  미세 먼지 입자가 화면 전체에 서서히 흘러내린다. `decorate()`에서 매 장면 기본으로
  깔아주면 "우주/네온" 분위기가 확 산다 — `fibonacci.js` 참고.
- **`drawOrbitRing`으로 SF-HUD 느낌을 더한다**: 중심 도형 주위(또는 뒤)를 천천히 도는
  점선 타원 + 화살표 마커. 안전영역보다 크게 그리면 잘리니, 반지름은 항상
  `--safe` 가이드로 확인하고 안전영역 폭의 절반보다 작게 잡는다.
- **`drawFlare` + `drawBurst`로 아웃트로를 더 폭발적으로**: 로고가 나타나기 직전에
  밝은 방사형 플레어(`drawFlare`)를 깔고 그 위에 큰 `drawBurst`(count 40+, maxDist 400+)를
  터뜨리면 레퍼런스 영상 같은 "빛 폭발" 느낌이 난다 — `fibonacci.js`의 `renderOutro` 참고.
- **팩트체크/판정형 콘텐츠는 `drawStamp`를 쓴다**: 주장 텍스트 → 기울어진 도장이 통통
  튀며 "사실"/"과장" 같은 판정을 찍는 연출. `fibonacci_factcheck.js`가 예시다 — 속설을
  하나씩 검증하는 포맷이면 이 패턴을 재사용하세요.
- **`drawBurst`로 순간을 강조한다**: 공식이 완성되는 순간, 숫자가 확정되는 순간처럼
  "짜릿한 포인트"에만 방사형 파티클을 짧게 터뜨린다. 화면 전체에 계속 뿌리는
  `drawSparks`/색종이 효과와 달리, `drawBurst`는 0.3~0.6초짜리 순간 연출이라 차분한
  브랜드 톤을 깨지 않으면서도 포인트를 준다.
- **속사포 사례 목록**을 쓴다: 실제 숫자(행성/혜성/우주선의 이심률 등)를 1.5초 안팎으로
  빠르게 전환하면 정보 밀도와 리듬감이 동시에 올라간다(`renderReal` 참고).
